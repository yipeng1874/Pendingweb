## 1. 功能概述

仪表台（Cockpit）是本系统 PC 端的核心数据看板页面，路由为 `/tasks/cockpit`。  
面向有管理权限的用户（BASE_ADMIN 及以上），集中展示：

| 模块 | 说明 |
|---|---|
| 顶部 Hero | 使用天数 + 基地切换器 + 上传入口（星星按钮） |
| 历史待办完成率 | 昨天 / 近3天 / 近7天 / 本月（可自定义日期）的投放完成率环形图 |
| 基地直播间空余 | 按「基地→场地→房间类型→团队」四级展示直播间占用 |
| 主播数量统计 | 基地维度的主播总数/7天内新增/20天内新增（v9 已移除趋势图） |
| 厅/主播运营 KPI | 正式厅、训练厅、近30天主播流失、人均音浪 |
| 情况 | 今日投放/完成/进行中/未开始/豁免 |
| 过程指标 | 按团队+厅+日期的完成率趋势折线图，参与团队配置（服务端共享），单条删除 |
| 留存率看板 | 按团队+月份的留存率上传与展示 |
| 员工流失看板 | 按团队+日期上传 8 项指标（离职线上/线下各2 + 在职线上/线下各2），4象限趋势图（人数/音浪 × 在职/离职），右侧纵向指标列显示人数和 & 音浪均值 |

**已搬迁**：
- 「我的待办汇总」→ 路由 `/tasks/dashboard`（TaskDashboardPage）

### 4.10 StaffTurnoverDaily（在职/离职人数音浪 — v10 重构）

> **v10 重大重构**：将原来的单一 `turnoverCount` 字段拆分为 **离职×线上/线下**（4 字段） + **在职×线上/线下**（4 字段），共计 8 个业务指标。同时保留 `lossCount` / `lossAvgWave` 作为加权合计值（写入时自动计算）。

```prisma
model StaffTurnoverDaily {
  id                   String   @id @default(uuid())
  baseOrgId            String   @map("base_org_id")
  baseOrgName          String   @map("base_org_name")
  teamOrgId            String   @map("team_org_id")
  teamOrgName          String   @map("team_org_name")
  recordDate           String   @map("record_date")
  // 离职合计（写入时自动计算 = 线上+线下）
  lossCount            Int      @map("loss_count")
  lossAvgWave          Float    @map("loss_avg_wave")
  // 离职 · 线上 / 线下
  lossOnlineCount      Int      @default(0) @map("loss_online_count")
  lossOnlineAvgWave    Float    @default(0) @map("loss_online_avg_wave")
  lossOfflineCount     Int      @default(0) @map("loss_offline_count")
  lossOfflineAvgWave   Float    @default(0) @map("loss_offline_avg_wave")
  // 在职 · 线上 / 线下
  activeOnlineCount    Int      @map("active_online_count")
  activeOnlineAvgWave  Float    @map("active_online_avg_wave")
  activeOfflineCount   Int      @map("active_offline_count")
  activeOfflineAvgWave Float    @map("active_offline_avg_wave")
  uploadedBy           String   @map("uploaded_by")
  uploaderName         String   @map("uploader_name")
  createdAt            DateTime @default(now()) @map("created_at")
  updatedAt            DateTime @updatedAt @map("updated_at")

  @@unique([teamOrgId, recordDate])
  @@index([baseOrgId])
  @@map("staff_turnover_dailies")
}
```

**业务说明**：
- 每条记录包含 **8 个业务字段**：离职线上人数/音浪、离职线下人数/音浪、在职线上人数/音浪、在职线下人数/音浪
- `lossCount` = `lossOnlineCount` + `lossOfflineCount`（自动求和）
- `lossAvgWave` = Σ(线上人数×线上音浪 + 线下人数×线下音浪) / 总人数（加权平均）
- `activeOnlineCount` / `activeOfflineCount` 是"在职但尚未离职"的员工人数，按线上/线下分类
- upsert 覆盖同团队同日期数据

**v10 数据库迁移对照**：

| 字段 | v9（旧版） | v10（新版） | 迁移方式 |
|---|---|---|---|
| `turnover_count` | 离职人数（单列） | **已废弃** | Prisma 层面删除，数据库列可保留（向后兼容） |
| `loss_count` | — | 离职合计人数 | 新增（由 v10 自动计算替代旧 turnoverCount） |
| `loss_avg_wave` | — | 离职加权音浪 | 新增 |
| `loss_online_count` | — | 离职 · 线上人数 | `20260725000000_split_loss_to_online_offline` |
| `loss_online_avg_wave` | — | 离职 · 线上音浪 | 同上 |
| `loss_offline_count` | — | 离职 · 线下人数 | 同上 |
| `loss_offline_avg_wave` | — | 离职 · 线下音浪 | 同上 |
| `active_online_count` | — | 在职 · 线上人数 | 架构新增（v10 prisma schema） |
| `active_online_avg_wave` | — | 在职 · 线上音浪 | 架构新增 |
| `active_offline_count` | — | 在职 · 线下人数 | 架构新增 |
| `active_offline_avg_wave` | — | 在职 · 线下音浪 | 架构新增 |

## 5. 过程指标（v9 重点）

### 5.1 架构设计

```
前端 ProcessMetricCard
  ↓ scopeOrgId
  ↓ 并行请求：
  ├── GET /process-metric/config   → 读取参与团队配置（服务端存储，同一基地所有用户共享）
  ├── GET /process-metric/by-date  → 读取过程指标数据
  └── fetchOrgTree()               → 获取组织树（用于团队列表）

删除：
  上传弹窗中点击删除按钮 → DELETE /process-metric
    ↓ 用位置（idx）在 dateEntries 里找回原始厅名
    ↓ 用原始厅名调后端删除
    ↓ 删除成功 → 本地更新 dateEntries（图表实时刷新）
```

### 5.2 参与团队配置（服务端共享）

**之前的问题**：`participatingTeamIds` 存在 React 本地 state，A 账号配置的团队 B 看不到。

**v9 解决方案**：`process_metric_configs` 表，按 `baseOrgId` 主键存储 `teamIds` JSON 数组。

**接口**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/process-metric/config?scopeOrgId=xxx` | 读取该基地的参与团队 ID 列表 |
| PUT | `/process-metric/config?scopeOrgId=xxx` | 保存参与团队 ID 列表（全量覆盖） |

**前端行为**：
- 首次加载：fetch config，如果服务端有配置则使用；如果为空则自动检测有数据的团队并保存到服务端
- 每次切换参与团队：`toggleParticipatingTeam` 立即调 PUT 保存
- 全选/全不选：一次性保存到服务端

### 5.3 删除功能

**场景**：A 团队有多个厅，想删除某个厅的数据。

**实现**：

| 方法 | 路径 | 参数 |
|---|---|---|
| DELETE | `/process-metric` | `?scopeOrgId=xxx&teamOrgId=xxx&hallName=xxx&recordDate=xxx` |

**前端逻辑**：
1. 用户点击删除按钮
2. 用 **idx 位置** 在 `dateEntries` 中找到**原始厅名**（防止用户改过名导致匹配失败）
3. 用原始厅名调 DELETE 接口
4. 成功 → 本地更新 dateEntries，图表实时刷新
5. 404 → 忽略（说明数据库本来就没有）

**权限**：TEAM_ADMIN 和 HALL_MANAGER 无权删除（返回 403）

### 5.4 全部接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/process-metric/upsert?scopeOrgId=xxx` | 覆盖写入单条 |
| POST | `/process-metric/upsert-batch?scopeOrgId=xxx` | 批量覆盖写入 |
| GET | `/process-metric/by-date?scopeOrgId=xxx&days=6` | 按日期查询（最近 N 天，含团队、厅分组） |
| GET | `/process-metric/latest-halls?scopeOrgId=xxx&teamOrgId=xxx` | 某团队最近一次的厅列表 |
| GET | `/process-metric/config?scopeOrgId=xxx` | 读取参与团队配置 |
| PUT | `/process-metric/config?scopeOrgId=xxx` | 保存参与团队配置 |
| DELETE | `/process-metric?scopeOrgId=xxx&teamOrgId=xxx&hallName=xxx&recordDate=xxx` | 删除单条记录 |

## 13. 开发时新增模型流程

1. 修改 `backend/prisma/schema.prisma`
2. 执行：
   ```bash
   cd backend
   npx prisma migrate dev --name add_your_model_name
   ```
3. 提交迁移文件和 schema.prisma 到 Git
4. 推送后生产环境执行 `npx prisma migrate deploy` + `npx prisma generate`
5. 对于 ALTER TABLE 等已有表的变更，Prisma Migrate 会生成增量 SQL
6. 如果只改 Prisma 类型注解（不改表结构），只需 `npx prisma generate`
